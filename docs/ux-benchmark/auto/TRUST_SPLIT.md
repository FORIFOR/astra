# Trust を 2 つに割る

「このUIをどれくらい信頼できますか」を 7 段階で聞くのをやめた。
**採点者に心理状態を直接当てさせない。**

## 1. Holistic Trust — 測れない

「この AI に日常の仕事を任せられるか」。会話の正確さ、失敗の経験、
復旧、時間の経過が要る。**静止画 1 枚では原理的に決まらない。**

```
HOLISTIC_TRUST = NOT_MEASURED
Evidence = D
AUTO_FIX_ELIGIBLE = false
```

総合ゲートから**外す**。「人が見るまで BLOCK」ではなく、
自動では測れないものとして扱う。

## 2. Trust Affordance — 測れる

画面に何が在るかは、見れば分かる。7 段階ではなく **YES / NO** で聞く。

```
provenance_visibility        誰が言ったか分かるか
                             いつ言ったか分かるか
provenance_discoverability   原文へ戻る手段が見えるか
                             音声へ戻る手段が見えるか
correction_discoverability   誤りを直す手段が見えるか
action_transparency          AI が作ったものと出典の関係が分かるか
```

**正解は機械で分かる。** fixture は「その要素を消した／ずらした／偽った」姿なので、
何が YES で何が NO かは、作った側が知っている。当てられるかを測ればよい。

## 欠陥の型（fixture）

| 型 | 何を壊すか |
| --- | --- |
| `bad-no-source` | 出所を完全に消す |
| `bad-ambiguous-source` | 話者だけ。時刻も原文への道も無い |
| `bad-wrong-hierarchy` | 出所は在るが、その項目から遠い場所に置く |
| `bad-fake-confidence` | 根拠が無いのに「確認済み」と出す |
| `bad-contradictory` | 拾った文と、引いた原文が食い違う |

`bad-fake-confidence` と `bad-contradictory` を**高く**採点する採点者は、
Trust の評価者として不適格。出所の見た目だけを見て、中身を見ていない。

## 棄権を許す

`YES` / `NO` / `INSUFFICIENT_EVIDENCE` の 3 択にする。
「この絵からは決まらない」と言えることは、良い挙動。
無理に点を付けさせる方が危ない。

## 結果（2026-09-02）

fixture 8 枚（good 2 / good-open 1 / 欠陥 5 型）、Judge 3 体、YES/NO/棄権。
**正解は作った側が知っている**ので、当てられたかを機械で数えられる。

```
問い            正答
speaker         23/24   96%
time            23/24   96%
to_source       23/24   96%
to_audio        24/24  100%
to_fix          24/24  100%
────────────────────────────
観察できる 5 問  97.5%   誤って在ると言った 1.7%  見落とし 5.8%  棄権 0.8%
────────────────────────────
grounded        17/23   74%   ← 判断を要する問い
```

**分かれ目がはっきり出た。**

- 画面に何が在るかを聞くと **96〜100%** で当たる
- 「本当に結び付いているか」を聞くと **74%** に落ちる

```
TRUST_AFFORDANCE = PASS   → Evidence B。この軸で A/B/C 探索を再開してよい
grounded         = NOT_MEASURED
HOLISTIC_TRUST   = NOT_MEASURED（静止画 1 枚では原理的に決まらない）
```

### 絵ごとの成績

```
NO_SOURCE          18/18   出所を消したことは、はっきり分かる
GOOD_OPEN          18/18
AMBIGUOUS_SOURCE   17/17
CONTRADICTORY      17/18   食い違いは見抜けている
FAKE_CONFIDENCE    17/18   「確認済み」の空証明も見抜けている
GOOD               16/18
WRONG_HIERARCHY    15/18   ← いちばん弱い。出所が遠い場合の判断が割れる
```

`FAKE_CONFIDENCE` と `CONTRADICTORY` を見抜けているのは重要。
**出所の見た目だけを見て中身を見ない採点者ではない。**

### 途中で直した、正解表の誤り 2 件

自分で絵を見て気付いた。**採点者ではなく、私の正解が間違っていた。**

- `FAKE_CONFIDENCE` は時刻と話者が残る（消したのは出所への道だけ）
- `CONTRADICTORY` は**開かないと食い違いが見えない**。閉じた絵で撮っていた

# continuity と delight も同じ形に割った

心理状態を聞くのをやめ、観察できる問いへ。**問いごとに昇格を決める**
（軸をまとめて合否にすると、測れる問いまで巻き添えで落ちる）。

## delight

```
padding_even           80.0%   弁別なし（good と bad で答えが変わらない）
aligned                73.3%   Evidence C のまま
decoration_restraint  100.0%   ✓ Evidence B へ
```

**「楽しいか」ではなく「意味の無い飾りが無いか」なら 100% で当たる。**
余白の不揃いと行のずれは、この採点者には見えていない。

## continuity — 昇格ゼロ、ただし理由が二重

```
one_surface        33.3%   弁別なし
detached_overlay   33.3%   弁別なし
consistent_style   77.8%   Evidence C のまま（MISMATCHED は 3/3 で見抜く）
```

弁別が無いのは、**good も bad も同じ答えになった**から。
6 枚を並べた回では、3 体とも**全ての絵**で「別窓に見える」と答えた。

### ところが、2 枚だけ並べると答えが反転した

同じ base の絵に、同じ問い。並べる相手を変えただけ。

```
6 枚（明らかに剥がれた絵を含む）で聞く   one_surface  NO,NO,NO
2 枚（似た絵だけ）で聞く                 one_surface  YES,YES,YES
```

**同じ UI の同じ問いが、batch の中身で反転する。** これは製品の性質ではなく
採点の性質で、絶対採点を 1 枚ずつ別セッションにすべき理由そのもの。

`detached_overlay` は **NOT_MEASURED**。4 周目に「Dock が別窓に見える」を
根拠に造形を直そうとしたが、その根拠自体が安定していなかった。

### 直そうとした案は、そもそも見えなかった

凹みに座らせる案（offset 3 → 0、影を 0.27/14/5 → 0.08/4/1）を撮って出したところ、
3 体とも「2 枚に違いは無い」と答えた。**人にも機械にも区別できない変更**なので
採らない。4 周目に「continuity が上がらなかった」のは、案が弱すぎたのが理由。

---

# 一括 vs 1 枚ずつ — 順序効果は主因ではなかった

`one_surface` / `detached_overlay` の答えが並べる絵で反転したので、
1 枚 1 セッションで測り直した（6 枚 × 2 体 = 12 セッション）。

```
絵     型          問い              正解  一括          1枚ずつ
F8D0  DETACHED   one_surface       NO    NO,NO,NO      NO,NO
F8D0  DETACHED   detached_overlay  YES   YES,YES,YES   YES,YES
2900  GOOD       one_surface       YES   NO,NO,NO      NO,NO
2900  GOOD       detached_overlay  NO    YES,YES,YES   YES,YES
5F3D  GOOD       one_surface       YES   NO,NO,NO      YES,NO
4681  MISMATCHED one_surface       YES   NO,NO,NO      NO,YES

正答  一括 33%   1 枚ずつ 46%
```

**条件を変えても答えはほとんど変わらなかった。** 順序効果はあるが主因ではない。

## 主因は、私の正解表だった

`GOOD` の絵についても、独立した観測 **8/9 が「別窓に見える」**と答えている。
一括でも 1 枚ずつでも、Sonnet でも Haiku でも。採点者どうしは一致していて、
**一致していないのは私とだけ**。

私が `GOOD = one_surface YES` と書いたのは、**実装が 1 つの窓だと知っているから**。
だが聞いているのは見え方であって、実装ではない。答えは観測の側にある。

```
detached_overlay（base の UI）= 別窓に見える  ← 8/9 の観測
```

対比（座って見える版）を作れていないので、この 2 問には正の対照が無い。
正解表から外し、**NOT_MEASURED のまま**にする。ただし観測は残す。

## 座らせる案は、そもそも見えなかった

offset 3 → 0、影 0.27/14/5 → 0.08/4/1 では、3 体とも「2 枚に違いは無い」。
**人にも機械にも区別できない変更**なので、これでは対照にならない。
対照を作るには、もっと強い変更（凹みの形そのもの、あるいは地の共有）が要る。

## この節から言えること

4 周目に「Dock が別窓に見える」を根拠に造形を直そうとして、案が全部落ちた。
当時の判断は「仮説が外れた」だったが、正しくは:

- **観測は正しかった**（別窓に見えるのは本当）
- **案が弱すぎて対照にならなかった**
- **正解表が観測と食い違っていた**ので、精度としては測れなかった

---

# 対照が取れた — ただし採用しない

3px と影では誰にも見えなかったので、構造から変えた 3 案を 1 枚 1 セッションで測った。

```
案              one_surface   detached_overlay
BASE            NO,NO         YES,YES
shared-ground   NO,YES        YES,NO
inset           NO,NO         YES,YES
in-header       YES,YES       NO,NO      ← 反転
```

Judge の弁も一致している。

```
BASE       「黒い pill が白い面の枠から はみ出して 浮いている」
in-header  「2 枚のカードが 一つの外枠の中 に収まり、浮いた要素が無い」
```

**これで `detached_overlay` は初めて弁別できる尺度になった**（対照が存在する）。
同時に、8/9 の観測が正しかったことも確定した。

## それでも採用しない

Task Dock は録音中だけの面ではない。待機・Listening・Task・会議を貫く
**同じ一つの面**として設計されている（`ASTRA_UX_PRINCIPLES` §2 ONE SURFACE）。
会議の面でだけ消すと、その連続性が切れる。

**一つの軸を上げて別の軸を壊す**典型で、しかも壊れる側（状態をまたぐ連続性）は
静止画では測れない。測れる軸だけを見て、測れない軸を壊すことになる。

## 途中で分かったこと

`in-header` の 1 回目の絵には、面の中の操作と浮遊 Dock が**両方**写っていた。
分岐が当たっておらず、Dock が消えていなかった。撮った絵を見て気付いた。
そのまま出していたら「消しても別窓に見える」という誤った結論になっていた。

窓の一覧も確認した。Astra の窓は **1 つだけ**（420,175 1080x680）。
「別の窓に見える」のは見え方の話で、実際に窓が増えているわけではない。
`windowsOpened = 0`（Evidence A）と矛盾しない。

## 次にやるなら

Dock を消さずに「枠からはみ出して見える」だけを直す案が要る。
Judge の弁は一致して**「白い面の枠から上へ突き出している」**。
凹みの形と Dock の高さの関係を見直すのが筋で、これは造形の設計判断。

# 凹みの寸法では動かなかった — 主因は素材だった

Dock を消さずに「はみ出し」だけを直す案を 2 つ測った。

```
案              one_surface   detached_overlay
BASE            NO,NO         YES,YES
deep-notch      NO,NO         YES,YES     凹み 25 → 50（Dock 42 を収める）
fitted-notch    NO,NO         YES,YES     深さ＋幅も Dock に合わせる
```

**両案とも変わらなかった。** Judge の弁を並べると理由がはっきり出る。

```
BASE          「黒い pill が白い面の上端から突き出している」「影がある」
deep-notch    「暗い pill が上端から突き出している」「影があり、浮いている」
fitted-notch  「黒い制御バーが白い窓の上に浮いている」「影と角丸」
```

寸法の話をしているのは私だけで、**Judge は一貫して素材の話をしている**。
黒い塊が白い面に載っていて影を落としている構図は、凹みを深くしても変わらない。

## 5 案を通して分かった主因

```
in-header      浮遊をやめる          2/2 反転   ← 効く
shared-ground  地を共有する          1/2 部分的 ← 効きかけ
inset          影と隙間を無くす      0/2
deep-notch     凹みを深くする        0/2
fitted-notch   凹みを Dock に合わせる 0/2
```

**素材と影が主因で、凹みの寸法は主因ではない。**

## ここで自動探索は止まる

素材を変えずに直す道は、5 案では見つからなかった。残る選択肢は 3 つで、
**どれも設計の意思決定**にあたる。

```
(a) 黒い素材をやめる            Astra の看板要素の変更
(b) 会議の面では Dock を面の中へ ONE SURFACE の連続性と引き換え
(c) 直さない                    「別窓に見える」を仕様として受け入れる
```

自動探索が決めてよい範囲を超えている。**測定は終わり、判断が要る。**
