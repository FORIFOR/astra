# Astra: 目的から成果物を作る実行基盤

2026-09-11のユーザーによる製品方針。ここに記す新しい能力は、明記した修正以外は**実装目標**であり、現在の対応済み機能を表さない。

## 成功の定義

Astraは、小さな依頼から複数工程の仕事まで、相手のニーズを調べ、使える成果物を作り、検証・改善し、実際の反応まで追える製品を目指す。最初の利用者は開発者本人。最初の用途は、Astraを使って独自の面白い動画を制作し、YouTube・TikTok・Xで反応を得ること。Astraの紹介動画に限定しない。

「エージェントが動いた」「返答が出た」「動画ファイルが存在する」だけでは完了しない。作品の出来、依頼との一致、実際に再生・利用できること、費用と人の手数を評価する。拡散や売上は事前に保証できるスコアではなく、公開後の実績として扱う。

## コードから確認した現在地

| 領域           | 現在の実装                                                                         | 今回のゴールに対する不足                                                   |
| -------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| タスク実行     | Temporalの工程実行、確認、イベント、成果物保存                                     | 制作結果を評価して計画・一部分を直す反復ループ                             |
| 動画           | `services/agent-runtime/src/video.ts`にクリップ、構成、タイムライン、字幕          | 実生成、素材の一貫性、音声、合成、再生検査                                 |
| 動画の接続     | `workers/task-worker/src/worker-main.ts`が`videoExecutors`へrendererを渡していない | 現在の`video.render`では完成動画を作れない                                 |
| 制作環境       | `workers/agent-host/src/codex.ts`は一時フォルダ・read-onlyで文章を返す             | 指定した作業領域でコードを書く・実行する・プレビューして直すための専用経路 |
| 動画担当worker | `workers/media-worker/src/index.ts`は会議系のtool一覧のみ                          | 長時間の動画生成ジョブ・編集の再開処理                                     |
| 株式           | `stock-executor.ts`に監視銘柄、保有比率、注文下書き                                | 戦略コード、履歴データ、時系列検証、ペーパー取引                           |
| 費用           | LLM等の自動重複実行防止                                                            | 動画生成の重複防止、見積・予約・実績を伴う仕事単位の上限                   |

この方針の最初のコード修正として、`video.render`の応答が失われた場合に、取り消せるファイル出力という分類だけで有料生成を自動再送しないようにした。新しいTemporal patch markerを使い、古い履歴の再生では従来の実行ポリシーを維持する。これは動画生成の接続完了を意味しない。

## 共通の実行経路

目的・相手・求める成果物・予算を受ける → 根拠を調べる → 実行可能な計画を作る → 専用作業領域で制作する → 実物を開いて評価する → 必要箇所だけ直す → 成果物と検証結果を渡す → 実績から次の企画を改善する。

各仕事に以下を保存する。

- **依頼**: 誰の何を解決するか、利用先、成果物、利用可能な素材と権限、完了条件。
- **計画と実行**: 工程の依存関係、使用する能力、入力・出力の版、プロバイダのjob ID、再開地点、停止理由。
- **費用**: 見積の根拠・日時、上限、予約額、実績、上限不明の操作。生成回数や上限時間も別に持つ。
- **成果物**: 実ファイル、プレビュー、編集可能なソース、使い方、根拠・素材の出所。
- **評価**: 技術検査、依頼への適合、創作品質、人の判定、公開後の実績。未検証と失敗を成功へ丸めない。

通常の文章回答は既存の制限付き経路を保つ。制作には別の実行インターフェースを設け、仕事専用のworkspaceへの書き込みと必要なCLI・ブラウザだけを渡す。既存の安全設定を一括解除して制作機能に代用しない。秘密情報はモデルの文章に混ぜず、接続アダプタが扱う。

画面は既存の依頼欄・進捗・成果物プレビューを使う。ユーザーには目的・成果物・費用・必要な判断を見せる。モデル名やtool一覧を仕事の入口にしない。

## 最初に通す一連の仕事: オリジナル短編動画

標準依頼例:「日本語で、一目で面白さが伝わるAI短編を作って。YouTube Shorts、TikTok、X向け。企画選びから投稿素材まで進めて。」尺30〜45秒・企画3案・最初の完成作1本を初期値とする。これは検証用の製品設定案で、各SNSの仕様を断定するものではない。

1. 相手・ジャンル・参考のどこを取り入れるかを定める。参考URLの取得失敗を見たことにしない。
2. 3案を作り、冒頭の分かりやすさ、意外性、展開、実現性、費用を比較して1案を選ぶ。候補の大量生成を既定にしない。
3. 登場人物・場所・映像の調子を決め、ショット割り・台詞・効果音・カメラを作る。同じキャラクターの基準素材を各カットに使う。
4. 利用可能な生成先と見積を確認する。契約・API接続・予算が足りなければ、具体的に何が必要かを示す。静止画スライドで完成映像の代役を作らない。
5. キーカットを先に作り、成立を確かめてから残りを作る。受理済みjobは保存して照会し、アプリ再起動やタイムアウトで再生成しない。成否不明は予算予約を解放しない。
6. 映像・会話・効果音を編集し、必要な字幕を加える。説明文だけが動く作品を、この用途の品質合格にしない。
7. デコード、尺、画角、黒画面・静止、音声、字幕のはみ出しを機械検査する。キャラクターの連続性、台詞との一致、面白さは映像を見て評価する。修正は不合格カット単位にし、同じ設定の無制限な再試行をしない。
8. MP4、カバー、投稿文、編集用ソース、素材一覧、費用、検査結果をまとめて渡す。投稿は接続先・内容の確認後に実行する段階として切り分ける。

実生成APIにも差がある。[PolloのQuick Start](https://docs.pollo.ai/quick-start)は生成と状態照会の分離を説明し、[RunwayのルーターAPI](https://docs.dev.runwayml.com/model-routers/generating/)はdry runでの見積経路を提供する。接続先を抽象化しつつ、見積精度・job照会・音声・参照画像・対応尺は実際のモデル契約で検証する。

## 受け入れ条件と順番

| 順番                    | 受け入れる成果                         | 合格条件                                                                                                                             |
| ----------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1. 動画制作             | 独自企画の完成動画1本と投稿用一式      | Astraの依頼から実生成・編集・検査・受け渡しまで通る。途中の手作業をすべて記録                                                        |
| 2. 再現性               | 異なる企画で3回の完走                  | 停止・再開、生成失敗、不良カットの修正、費用上限での停止も検証。見せられない出来を完走に数えない                                     |
| 3. 実績                 | 本人が公開した作品の比較記録           | 取得できる範囲の視聴維持・共有・プロフィール/サイトへの遷移と、制作費・人の作業時間を比較。単純な再生数だけで判定しない              |
| 4. Web提案              | 対象企業に合う改善サイトと提案一式     | 現状調査、動くプレビュー、モバイル表示、導線・アクセシビリティ・性能、変更理由、提案文まで。外部送信は別の明示操作                   |
| 5. 売買シミュレーション | 動く戦略コードと再現可能な検証レポート | データ期間、時系列分離、手数料・スリッページ、ベンチマーク、損失・ドローダウン、ペーパー取引を確認。利益の予測と測定結果を混同しない |

録音やConnectionsは、この共通基盤へ文脈と素材を供給する機能として維持する。動画・Web・株式の専用画面を同時に増やすことを、最初の成功条件にはしない。

## 今回の検証範囲

動画生成受理後に応答を失う条件を模擬したテストは、修正前に5回の実行を検出して失敗した。修正後は、新しい履歴で1回、旧patch markerの履歴で従来の5回という選択を確認した。タスク系54件・既存動画系20件の計74件とTypeScript buildが成功。これはプロバイダを注入したコード検証で、Temporalサーバの履歴リプレイ検証や有料動画の実生成ではない。今回の新しい制作機能の公開・デプロイ・SNS投稿は行っていない。
