## 読み上げの first-byte と、揃うまで

正本 §23 は「first-byte / playback latency を計測」と言っている。
**合計だけを測っていた間、「待たされた」という感覚がどこから来るのかが
見えなかった。**分けて測った:

|               | 最初の音まで | 揃うまで |        差 |
| ------------- | -----------: | -------: | --------: |
| 短文（33KB）  |        689ms |    697ms |       8ms |
| 長文（589KB） |      1,144ms |  1,306ms | **162ms** |

短文では両者がほぼ同じ。長文で 162ms 開く。
体感を決めるのは前者で、そこは文の長さで倍近く変わる。

この endpoint は音をまとめて返すので、**厳密な first-byte は取れない**。
取れるのは「提供者が答え始めた時刻」で、それが体感に一番近い。
取れないものを取れたことにしないよう、何を測っているかをコードにも書いた。

再生（playback）そのものの遅延は**測っていない**。実際の音声出力が要る。

## 超過について

3 つとも**代役では絶対に出ない数字**で、実接続にして初めて見えた。

- **会議の字幕 2.76s**（予算 900ms）。Google STT V2 の streaming が
  最初の partial を返すまでの時間そのもの。こちら側の処理ではないので、
  縮めるには「手元の軽い認識を先に出し、あとで置き換える」形にするしかない。
  そのための手元 STT は入っているが、**それも 1.5s かかる**（下記）
- **手元の最初の partial 1.53s**（予算 350ms）。内訳は窓 1,500ms + decode 29ms。
  **遅いのは decode ではなく窓。**窓を 700ms にすると 21 字（誤りが増える）、
  1,500ms で 35 字、6,000ms で 42 字（正解）と、精度と真っ向から引き換えになる。
  14 秒の録音を丸ごと起こすと 246ms で正解が出る
- **最初の根拠まで 21s**（予算 4s）。端末の web 検索が 15.8s を占める。
  Claude Code が検索して要約して返す往復で、この経路である限り縮まない

## 測っていないもの

| 目標              | なぜ測っていないか                                                                      |
| ----------------- | --------------------------------------------------------------------------------------- |
| `dockShow`        | 実際の描画が要る。assistant は画面を操作していない                                      |
| `micCaptureStart` | 実マイクが要る。無音デバイスでは数字の意味が変わる                                      |
| `textFirstToken`  | 端末のモデル経由になった。**最初の 1 文字**を測る場所がまだ無い（CLI は返事全体で返る） |

いずれも「まだ測っていない」であって、「守れている」ではない。
